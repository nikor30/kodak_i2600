# Decisions (ADR log)

Format: ID, date, context, decision, consequences. Never delete; supersede with a new ADR.

## ADR-001: Three-path strategy (2026-09-28)
- **Context:** no ARM driver exists; a full clean-room driver takes months.
- **Decision:** A) vendor x86 driver via box64 on the Pi as the interim solution; B) protocol capture/RE; C) native SANE backend.
- **Consequences:** the Paperless pipeline can be built early; the driver must stay swappable behind SANE.

## ADR-002: Linux vendor driver is the primary RE target, Windows is secondary (2026-09-28)
- **Context:** Linux `.so` files are easier to analyse (ELF, likely symbols, libusb), and usbmon/LD_PRELOAD make tracing cheap.
- **Decision:** start RE on the Linux driver; use the Windows driver only for features missing on Linux.

## ADR-003: Git-versioned project memory (2026-09-28)
- **Decision:** `CLAUDE.md` + `memory/*.md` are the long-term memory. They are updated and committed every session (`memory:` prefix).

## ADR-004: Clean-room separation & no vendor code in git (2026-09-28)
- **Decision:** `vendor/` is git-ignored; `re/` holds facts/notes only; `backend/` is written from `docs/protocol/` only.

## ADR-005: Capture tool is a libopenusb shim, not a libusb LD_PRELOAD (2026-09-28)
- **Context:** the vendor driver does not use libusb. It `dlopen`s libopenusb from `/usr/local/lib{,64}/libopenusb.so` (F-012).
- **Decision:** `tools/openusb-logger/` will be a drop-in `libopenusb.so` that logs every `openusb_*_xfer`/`xfer_aio` (pipe, endpoint, direction, length, hex payload, timestamp) and forwards to the real library. usbmon + Wireshark stays as the independent cross-check.
- **Consequences:** logs carry driver-level context (which pipe: BulkOut/ImageFront/…), not just raw URBs.

## ADR-006: Vendor installer is not run on target systems (2026-09-28)
- **Context:** postinst edits `50-udev-default.rules`, sets MODE 666 udev rules, and runs `chmod -R 777 /var/kodak`.
- **Decision:** on the Pi and on reference machines, unpack the `.deb` files manually and install our own minimal udev rule. Use a VM or a throw-away install if the vendor `setup` is ever needed.

## ADR-007: Phase 1 uses a Debian amd64 chroot + qemu-user first, box64 second (2026-09-28)
- **Context:** the vendor stack hard-codes absolute paths (`/opt/kodak`, `/usr/local/lib/twain`, `/usr/local/lib/libopenusb.so`, `/var/kodak`) and needs a full x86 SANE userland. Box64 running from the host would need those paths on the Pi's root filesystem plus a mixed-arch library setup.
- **Decision:** build an isolated `/opt/kodak-x86` bookworm amd64 chroot (debootstrap) run via qemu-user binfmt. Vendor debs are merged safely (F-021). The chroot SANE loads only `kds_i2000`. Box64 is tried only if qemu is too slow.
- **Consequences:** easy to undo (delete the directory); slower than box64. In Phase 5, native tools can reach it via an x86 `saned` on localhost plus the SANE `net` backend.

## ADR-008: Fake x86 /proc/cpuinfo inside the chroot (2026-09-28)
- **Context:** under qemu-user the vendor's image-processing helper (hippo.so via lexexe) hangs after parsing the host's ARM /proc/cpuinfo (F-026).
- **Decision:** the chroot's own procfs gets an x86-style cpuinfo (one entry per host CPU, `cpu MHz: 1800`, physical/core ids, SSE4.2-level flags), bind-mounted over `$ROOT/proc/cpuinfo` only. It is removed with the chroot's `/proc` on umount.
- **Consequences:** the host is unaffected. If hippo also uses CPUID to choose AVX code paths, qemu's CPU model decides that, not this file.

## ADR-009: box64 built from source, installed into the Kodak chroot (2026-09-28)
- **Context:** qemu-user works but is slow (≈30 s per duplex sheet, ~20 s open, F-031). The owner chose to try box64 for speed before building the Paperless pipeline. Debian trixie's box64 0.3.4 needs glibc ≥ 2.39; the Kodak chroot is bookworm (2.36), and moving the chroot to trixie risks breaking the vendor libs.
- **Decision:** `pi/phase1/setup-box64.sh` builds upstream box64 (pinned tag, `-DRPI4ARM64=1`) in a separate, disposable native arm64 bookworm chroot (`/opt/box64-build`), then installs the binary into `/opt/kodak-x86/usr/local/bin/box64` and adds `libc6:arm64` etc. to the Kodak chroot via multiarch. Use it with `kodak-x86 box64 <cmd>`; plain `kodak-x86 <cmd>` still uses qemu.
- **Consequences:** the host stays untouched (only the two /opt dirs). Both paths coexist, so we can A/B them. Child processes the driver spawns (deviceprobe, lexexe) may still fall back to qemu via binfmt unless box64 intercepts the execve; check this in the first run.

## ADR-010: Scan station = saned (box64, localhost) + native Python daemon, auto-start on paper (2026-09-28)
- **Context:** Phase 5. The vendor SANE backend exposes no button/LCD options (Q-022), and its open takes ~15 s. The owner chose REST API upload, color 300 dpi duplex, and auto-scan on paper.
- **Decision:** `kodak-saned.service` runs `saned -l -b 127.0.0.1` inside the chroot under box64. `kodak-scand.service` (native arm64 Python, python3-sane via the `net` backend, DynamicUser, token via LoadCredential) keeps the device open, polls `sane_start()` every 2 s (NO_DOCS returns immediately, F-035), scans the stack into one PDF (img2pdf) and uploads it via `/api/documents/post_document/` from a disk spool with retry. Profiles live in `/etc/kodak-scan/config.yaml`; blank-page removal is done by the driver.
- **Consequences:** only SANE is between the service and the driver (swappable for the native backend). The trigger moves to the Start button/LCD once those are reachable (native backend, interrupt EPs). The chroot's saned accepts 127.0.0.1 only.

## ADR-011: OLED status display as a separate service fed by a status file (2026-10-01)
- **Context:** the owner's Pi has a Waveshare PoE HAT (B) with an SSD1306 OLED (F-037) and wants the IP and the scan activity on it. kodak-scand runs sandboxed (DynamicUser, PrivateDevices) and should not get I2C access.
- **Decision:** kodak-scand writes its state (`starting`/`ready`/`scanning` + pages/`error`, upload queue) to `$RUNTIME_DIRECTORY/status.json` (`/run/kodak-scan/`). A separate `kodak-oled.service` (root, I2C devices only) renders IP + state with a small built-in SSD1306 driver (smbus2 + PIL, no luma dependency). The fan controller at `0x20` is not touched.
- **Consequences:** the display is optional and independent of the driver path; other consumers (status web page) can read the same file. The Kodak LCD stays unused until Q-022 is solved.

## ADR-012: kodak-scand asks systemd to restart saned after repeated scanner errors (2026-10-01)
- **Context:** after a device I/O error the long-running saned/box64 process kept failing every open for ~29 h; a saned restart fixed it (F-038). kodak-scand is sandboxed (DynamicUser) and cannot call systemctl.
- **Decision:** after 3 scanner errors in a row (no successful poll or scan in between) kodak-scand exits with status 75. `ExecStopPost=+…` in the unit restarts `kodak-saned.service` on that status; `Requires=` and `Restart=always` bring kodak-scand back. A time stamp in the spool (`saned-restart`) limits this to once per 10 minutes, so a switched-off scanner does not cause a restart loop.
- **Consequences:** still only SANE between service and driver; with the native backend the same rule restarts whatever saned runs then. The root cause of F-038 stays open (Q-023).

## ADR-013: Phase 2 capture runs on the Pi itself with usbmon; ADR-005's shim is dropped (2026-10-08)
- **Context:** the owner wants the native driver now (the box64 stack is costly and unstable). The vendor driver already runs on the Pi, and the protocol turned out to be plain control requests (F-041), so raw URB captures are easy to read.
- **Decision:** capture with `tools/usbcap/usbmon_capture.py` (binary usbmon → pcap, full payloads) while the vendor driver runs under box64, and name requests from the vendor's own tables (F-043). No libopenusb shim (it would need an x86 toolchain and gives no extra information). Supersedes ADR-005; answers Q-017 (yes).
- **Consequences:** raw captures stay in `captures/local/` (git-ignored) because they contain firmware and scanned documents.

## ADR-014: Native driver is grown from a Python prototype with a request whitelist (2026-10-08)
- **Context:** the plan's target is a C SANE backend; the protocol is still being decoded and every new request must be tried against the only device we have.
- **Decision:** `tools/kdsprobe/` (Python, ctypes + libusb-1.0) is the test bed. It refuses any request that `docs/protocol/commands.md` does not class as safe (`R` reads now; `W` once documented). The C backend in `backend/` is written from `docs/protocol/` when a sequence is proven there: first status/buttons/LCD, then scanning.
- **Consequences:** never-send classes (`X`: NVRam/EEPROM/flash writes, firmware, calibration, diagnostics) stay out of both. The power-up firmware/FPGA load is unavoidable for a driver that must survive a power cycle; it needs its own decision (ADR to come) and a local firmware extraction step, since the images cannot be redistributed.

## ADR-015: Interim native scan station in Python, beside the vendor station (2026-10-08)
- **Context:** the owner asked for a native scan service with the Start button and LCD labels now. Native scanning works by replaying one captured sequence (F-056, F-057) and the image processing exists (F-059); a C SANE backend is still far off. The vendor station keeps going stale (F-054).
- **Decision:** `kodak-native.service` (`pi/scan-station/kodak_native.py`) drives the scanner directly through `kds_usb`/`kds_scan`/`kds_image` and reuses kodak-scand's spool, PDF and upload code. Start button + LCD function number select the profile (`native.functions`); function labels are uploaded to the LCD. It always scans color 300 dpi duplex and derives gray, black/white, simplex and blank removal in software. After a power cycle it runs the vendor driver once to load the firmware. `Conflicts=` with kodak-scand/kodak-saned; `DRIVER=native ./install.sh` switches.
- **Consequences:** this path does **not** go through SANE, which sets aside the "everything above the driver talks only to SANE" rule for the interim; the driver code is kept in its own modules so the daemon can move to a SANE backend later. The service runs as root (USB + chroot for the vendor fallback); the state directory moved from `/var/lib/private/kodak-scan` to `/var/lib/kodak-scan` (systemd migrates it in both directions). The vendor stack must stay installed until power-up init is native (Q-027).

## ADR-016: Native power-up by replaying a locally extracted capture, vendor driver as fallback (2026-10-08)
- **Context:** after a power cycle the scanner runs only a boot firmware (F-048); so far the vendor driver under box64 had to load the rest (F-065), which keeps the whole vendor stack a runtime dependency. ADR-014 and the `X*` class in `docs/protocol/commands.md` asked for an explicit decision before any code sends the power-up requests. A full-payload capture now exists (F-067).
- **Decision:** `Scanner.power_up()` (`pi/scan-station/kds_scan.py`) replays the vendor's own power-up open from a file the user extracts locally from their own capture (`tools/usbcap/extract_powerup.py` → `/etc/kodak-scan/firmware/powerup.json` + `.bin`, never committed). The whole file is checked against fixed allow-lists before the first request is sent; requests that write permanent storage (NVRam `35`, EEPROM `a2`, serial flash writes, firmware update `23`/`24`) are in no list, and the extractor drops the vendor's NVRam write and LCD upload. The replay starts only at firmware id 1 and must end at id 3. kodak-native tries it when the file exists and falls back to the vendor driver on any failure or when the file is absent.
- **Basis of the decision:** the code and the power-up file were already written and installed on the Pi earlier on 2026-10-08; the owner then asked to commit it and release it as v0.1.1. That request is taken as the go-ahead ADR-014 required (interpretation of the session, not a quoted statement about the risk). Reading of the hard rule "never touch firmware update commands": it covers persistent updates (`23`/`24`, flash); the power-up load goes to RAM and is what the vendor driver does at every power-on.
- **Consequences:** `20`, `21`, `a0`, `f1` are sent by our code, but only inside this replay. Several replayed requests (`18`, `a3`, `e0`, `f2`, `e2`) are still undecoded and are sent byte for byte as captured, so the file is valid only for the unit and driver version it was captured from (hypothesis until a second capture is compared). **Untested on the device** as of this ADR (F-067): the first power cycle will exercise it; if it fails the vendor fallback runs, and if the scanner is left in a state the fallback cannot handle, a second power cycle with the file moved away restores the old behaviour. The vendor driver stays a prerequisite (to make the capture, and as fallback). The C backend may implement the same replay from `docs/protocol/commands.md` section 6.

## ADR-017: First C SANE backend: out of tree, libusb directly, batch model, start sequence as a data file (2026-10-08)
- **Context:** owner asked to start N6 (native C driver for SANE). The scan start is still a replay of one captured sequence (Q-026), the scanner feeds a whole stack on its own, and the raw image needs host processing. `libsane-dev` ships only `sane.h`/`saneopts.h`, not the `sanei_*` helpers.
- **Decision:** `backend/` builds `libsane-kodak_i2x00.so.1` with a plain Makefile against `libsane-dev` and `libusb-1.0` (no `sanei_usb`). The start sequence is a text file converted from the committed JSON at build time and read at run time (`/usr/share/sane/kodak_i2x00/`, path in `kodak_i2x00.conf`), checked against the same request allow-list that `kds_dev.c` enforces on every request. One `sane_start` per side; the first one starts the batch, `NO_DOCS` ends it; unfetched raw pages are held in memory, then in unlinked files in `/var/tmp`. Image work in the backend is limited to sheet crop (no deskew) and colour/gray/lineart conversion; deskew and blank removal are left to frontends for now. Power-up init and LCD labels are not in the backend yet. The facts the C code needed and that were only in our Python code were first written into `docs/protocol/commands.md` §8 ("Driver procedure for a scan") and `image-processing.md`.
- **Consequences:** a frontend that scans one page and closes loses the rest of the stack (documented; Q-031). Upstreaming needs a port to `sanei_usb`/`sanei_config`/`sanei_thread`. Until the backend has scanned for real and can do power-up and labels, `kodak-native` stays the production path; afterwards the station can become a SANE client (python-sane or scanbd), which restores the "everything above the driver talks only to SANE" rule that ADR-015 set aside.

## ADR-018: The station becomes a SANE client of our own backend (`kodak-sane.service`) (2026-10-08)
- **Context:** owner asked to use our native C driver for the station's scans to Paperless. The backend now does power-up, function number, labels, sensors, scanning, deskew and colour (F-069 … F-082). ADR-015 had set the "everything above the driver talks only to SANE" rule aside for the Python driver.
- **Decision:** `pi/scan-station/kodak_sane.py` is a python-sane client: it writes its own SANE config directory (`/run/kodak-scan/sane.d`: only `kodak_i2x00`, with the profiles' labels and the power-up file), polls the sensor options `scan`, `function-number`, `page-loaded`, `cover-open`, and on Start scans the batch in Color or Gray. It adds what the backend does not do: blank-side removal, black/white from gray with `bw_threshold`, JPEG/TIFF, and reuses kodak-scand's spool, PDF and upload. It imports no driver module. `sudo DRIVER=sane ./install.sh` builds, self-tests and installs the backend system-wide (`make install`) and switches the services; `kodak-native` (Python driver) and the vendor station stay installed as fallbacks (`DRIVER=native`, default vendor). The backend's sensor reads were limited to one GetStatus per 2 s because the station polls several times a second.
- **Consequences:** the hard rule holds again for the running station. The backend is now visible to every SANE frontend on the Pi (`/etc/sane.d/dll.d/kodak_i2x00`), but only one program can have the scanner open, and the station holds it. Two image pipelines exist (Python `kds_image.py` for kodak-native, C in the backend); the C one has no rotation by 180° and its deskew has only been seen on straight sheets on the device. Processing is no longer spread over worker processes (the backend converts in `sane_read`), only the encoding runs in threads.

## ADR-019: Settings page as a small separate web service that only edits the config files (2026-10-08)
- **Context:** owner asked for a web page to control the station: Paperless address and token, which profile is on which button, display texts. The settings live in `/etc/kodak-scan/config.yaml` (root, with comments) and the token in `/etc/kodak-scan/paperless-token` (root, 600, never to be shown or committed).
- **Decision:** `pi/scan-station/kodak_web.py` + `kodak-web.service`, port 2600: Python standard-library HTTP server, one static page (`web/index.html`, `web/app.js`, no external resources), JSON API. It edits the YAML with `ruamel.yaml` so comments and unknown keys survive, validates everything server-side, writes atomically and keeps `config.yaml.bak-web`. The token is write-only: it can be set and tested, never read back. It does not control the station directly: `kodak-sane` watches the config and token files and ends itself when they change while idle; systemd restarts it (`RestartSec=5`), which also reloads the token credential. Access: HTTP Basic, user `admin`, random password created on first start in `/etc/kodak-scan/web-password`; changes need a JSON content type, a custom header and a matching Origin, so another site open in the browser cannot post settings. The service runs as root (it must write root-owned files) with systemd sandboxing (`ProtectSystem=strict`, only `/etc/kodak-scan` writable, no new privileges, restricted address families).
- **Consequences:** plain HTTP with one password is for a trusted home network only; whoever has the password can redirect scans to another Paperless address. kodak-native and kodak-scand do not watch the config (manual restart). New dependency `python3-ruamel.yaml`. The first save adds the page's explicit defaults (`jpeg_quality`, `bw_threshold`, `tags`) to each profile. The page offers function numbers 1–7 (SetSequenceNumber maximum 7).

## ADR-020: Destinations per profile, statistics, display info and "quiet" instead of a standby command (2026-10-08)
- **Context:** owner asked for scanning to an SMB share or an e-mail recipient, some statistics, the scanner going to standby, and the scanner's display showing time and scan counts because the HAT's OLED is not always visible.
- **Decision:**
  - *Destinations*: `pi/scan-station/kodak_deliver.py` adds `Smb` (through the `smbclient` program with a private auth file; no mount) and `Email` (smtplib) beside Paperless. A profile has `destination` (and optional `email_to`); `finish_job` writes it into the job's metadata and the uploader delivers each job to its destination, skipping a destination that failed in this round without blocking the others. Passwords live in root-only files (`smb-password`, `smtp-password`) like the Paperless token and are write-only on the settings page.
  - *Statistics*: counters in `<spool>/stats.json` (totals, per profile, per destination, per day for 400 days), started from what the spool still held; shown on the settings page (four figures, pages per day for 30 days, two tables).
  - *Display*: the backend renders a title plus small info lines (`kds_lcd_text`, line breaks) and exposes `label-1…7` as settable options; the station writes `Today N  Total N` and date/time under each profile's text, refreshing the selected function once a minute.
  - *Standby*: no command is sent. `39` SetPower and `31` EnergyStar are unclassified (arguments unknown; the vendor's Linux driver has no power option to capture), so the hard rule forbids guessing. Instead the backend got a `quiet` option (no GetStatus while idle; events still read) and the station sets it after `native.standby_after` idle minutes, removes the clock line and stops display updates; any event ends the rest. The backend logs power-state events other than the usual 3/4.
- **Consequences / open:** whether the scanner enters standby when left alone, whether the interrupt polling of the event pipe keeps it awake, and whether the first Start press after a rest is reported (Q-029, Q-033). The minute-wise label upload assumes type-1 labels are volatile (F-065: lost at power-off); if they were written to EEPROM this would wear it, so the clock can be switched off (`display_info`). SMB and SMTP are tested against stand-ins only (F-090). New package `smbclient`.
